# ADR 0007: Append-only persistence

## Status

Accepted.

## Context

KeyDB must survive restarts with `appendonly yes`, support `BGREWRITEAOF`,
and remain compatible with KeyDB's AOF command stream and truncation policies.

## Decision

- Implement AOF as a RESP command stream with `SELECT` tracking.
- Load AOF at startup when `appendonly` is enabled; fall back to RDB when the
  AOF is absent, then create a fresh AOF from the loaded dataset.
- Support `always`, `everysec`, and `no` fsync policies. Live appends are
  written through to the OS on every command; fsync is policy-controlled.
- Rewrite synchronously from the current dataset using variadic commands
  wherever possible (`RPUSH`, `SADD`, `HSET`, `ZADD`), with `PEXPIREAT` for
  TTLs.
- Preserve `aof-load-truncated` behavior: truncate to the last valid command,
  or to the start of an incomplete MULTI block, when enabled; otherwise fail
  startup with KeyDB-compatible error text.
- Reject non-RESP content with KeyDB's "Bad file format" error.
- AOF RDB preambles and automatic rewrite thresholds remain future work.

## Consequences

- `unit/aofrw.tcl` and `integration/aof.tcl` pass in full.
- Rewrites are synchronous, so `BGREWRITEAOF` blocks the event loop briefly;
  the API/status flags match the observable tests.
- Command-level propagation currently records the original write command.
  Commands with nondeterministic effects are normalized where required
  (`SPOP` → `SREM`), with more rewrite normalization to follow.
